# API v1

Base path `/api/v1`, JSON, camelCase. Errors are RFC 9457 problem details:
`502 wslc command failed` (detail = the CLI's message), `503 wslc is not
available`, `504 wslc command timed out`, `400 Invalid request`, `409 Not
possible now` (the state the verb needs is not there: a stopped container's
files, a backup not yet ready). Records live
in `src/WslcAgent.ApiClient/Contracts`; the typed client is `WslcAgentApi`.

## Who may call

The agent keeps its own login; a proxy in front adds
nothing to it. Every path needs one of:

- a **session**: the `wslc_agent_session` cookie a sign-in sets (HttpOnly,
  SameSite=Lax, Secure behind HTTPS, 7 days), or the same value as
  `Authorization: Bearer` / `X-WSLC-Token` (native clients), or as the
  `access_token` query of a WebSocket (a WebSocket carries no headers);
- the **API token** (`Authorization: Bearer` / `X-WSLC-Token`), for scripts and
  AI agents, MCP included;
- a caller **at the agent's machine**: a loopback address, asking for a
  loopback host, with no `X-Forwarded-For`, `X-Forwarded-Proto` or `Forwarded`
  header (a tunnel arrives from loopback too).

Public: `/login` (the sign-in screen), `GET /api/v1/health`, `GET|POST
/api/v1/login`, `POST /api/v1/logout`, and the UI's static files. A refused page
(`Accept: text/html`) is redirected to `/login?next=PATH`; a refused call gets
`401 Sign in required`, or `503 Internet login not set` (with how to set it) when
it came through a proxy and neither a password nor a token exists. The login
lives in `login.json` in the data folder: the username, the password as a salted
PBKDF2-SHA256 hash, the session signing key (renewed with the password, which
ends every session) and the API token.

container details: given the first time the agent sees the resource, kept
through every rename and recreate, and gone with the resource. A container is
known by its id, an image by its `repository:tag`, a volume by its name, a
network by its id. A list read in full (`/containers` with `all=true`, and
every read of the other three) reconciles the registry — names and ids that
changed behind the agent's back, resources that appeared or went — within the
selected session; `all=false` enters what it sees and drops nothing. The
agent's own remove and recreate (a container's, a network's) keep it current
as they act. A row the registry does not hold (a Files helper, a dangling
image) has `uid` 0.

Notes

- `ContainerSummary.ports` are `host:port->container/proto` strings read from
  the `com.microsoft.wsl.container.metadata` label when the CLI leaves
  `Ports` empty (it does on 2.9.x); no `inspect` round-trip is needed.
- Every command gets `--session NAME` when `Wslc:SelectedSession` is set,
  except `system session list|enter`.
- "In use" for images, volumes and networks comes from one
  `container list --all` per request: its `Image`, `Mounts` (named volumes
  only; bind paths are not volumes) and `Networks` columns. Images also carry
  the CLI's own `Containers` count when it prints one.
- Published ports (`ContainerSummary.ports[]`, `ContainerDetails.ports[]`)
  read `hostPort->containerPort`: no bind address,
  no protocol, duplicates (IPv4 + IPv6 of one binding) collapsed. `form.publish`
  keeps the bind address (`127.0.0.1:8085:80`).
- Every positional the CLI receives (names, ids, references) is refused when
  it starts with `-`, so user input can never become an option (400).
- `ContainerLaunchRequest` is the launch form: `image` (required),
  `name`, `command` (split like a shell), `entrypoint`, `memory`, `cpus`,
  `publish[]`, `volumes[]` (`source:target[:ro]`), `workdir` (a host path is
  remapped to the first volume's target, or `/workspace`; a host workdir with
  no volume becomes `workdir:/workspace`), `env[]`, `network`, `ip` (honoured
  on user-defined networks only), `networkAliases[]`, `connectNetworks[]`
  (`name` or `name 172.19.0.2`, attached after creation), `user`,
  `restartPolicy` (`no`, `unless-stopped`, `always`; agent-owned, never a CLI
  flag), `stopTimeout`, `healthCmd`, `healthInterval`, `healthTimeout`,
  `healthRetries`, `healthStartPeriod`, `noHealthcheck`, `start`. Flag order:
  `--name --memory --cpus --publish… --volume… --workdir --env… --entrypoint
  --network --ip --network-alias… --user --stop-timeout` then either
  `--no-healthcheck` or the `--health-*` flags, then the image and the command.
- The restart policy lives in `<DataDirectory>/restart-policies.json`
  (`Wslc:DataDirectory`, default `%LOCALAPPDATA%\WSLC-AI-Agent\data`):
  enrolled containers (`unless-stopped`, `always`) with the state the user
  last asked for. Two seconds after the agent starts, `always` entries and
  `unless-stopped` entries last asked to run get `container start`. The same
  pass runs again whenever the session the agent targets is started from the
  app or a tool, whether or not the session itself had to be started: stopping
  a session takes every container in it down, the start-up pass is long past,
  and the session itself is back on its own with the next command.
- MCP tools mirror these, served at `/api/v1/mcp` (35 today): `health`,
  `system_info`, `cli_activity`, `home_overview`, `list_sessions`,
  `switch_session`, `start_session`, `stop_session`, `list_containers`,
  `inspect_container`, `container_logs`, `container_stats`,
  `check_container_launch` (this project's, over `/containers/launch-check`), `run_container`,
  `create_container`, `start_container`, `stop_container`,
  `restart_container`, `set_restart_policy`, `exec_in_container`,
  `kill_container` and `remove_container`, `list_images`, `inspect_image`,
  `pull_image`, `tag_image`, `push_image`, `save_image`, `list_volumes`,
  `create_volume`, `inspect_volume`, `volume_containers`, `list_networks`,
  `create_network`, `connect_container_to_network`,
  `disconnect_container_from_network`, `inspect_network`, `network_topology`,
  `pull_status`, `parse_run_command` and `run_command_line`.
  `kill_container`, `remove_container`, `exec_in_container`, `stop_session`,
  `remove_image`, `remove_volume`, `remove_network`, `prune_images` and
  `prune_volumes` are gated: a client that can show an approval prompt is asked
  through its own, and one that cannot gets a confirm token to bring back on a
  second call. They ship off — `Mcp:AllowDestructiveTools` is `false` in
  `appsettings.json`, the default until Settings → MCP server writes
  `mcp.json` — and while off they are not listed at all. Both switches are read
  on every request, so saving one reaches the running agent with no restart.
  `mcp-skill/` holds the plan, what is still open, and the skill a client
  installs.
