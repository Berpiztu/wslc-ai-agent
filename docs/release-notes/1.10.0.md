## Plugins: code of your own inside the agent, under your control

What one installation needs and nobody else does, an application of yours
asking the machine for something only the machine can see, no longer has to
be written into the agent: it is a plugin, a standard ASP.NET Core hosting
startup in a .dll, kept in that application's own repository.

- **Settings → Plugins** installs one from a .dll of the agent's machine,
  switches it on and off and removes it, **at once, with no new start of the
  agent** or of what runs on it. A plugin is loaded only when installed and
  switched on there, never because its files are in a folder; at the agent's
  start every one switched on is loaded again.
- **It says what each one does.** The list shows whether it is switched on and
  loaded, its version, and why it could not be loaded when it failed; under
  it, its log.
- **Behind the agent's login.** A plugin's endpoints ask for what every call
  to the agent asks: a session, the API token, or a caller at the agent's own
  machine.
- **Every request it answers is in the log**, with who asked: the name the
  caller gives in `X-Caller` (a container sends its own), its address and its
  program. The Logs page has a **Plugins** filter for all of them, each line's
  source saying which plugin wrote it.
- A plugin runs with everything the agent may do on the machine: install only
  code you trust. Installing one is never offered to an AI assistant.
- How to write one: [plugins.md](https://github.com/Berpiztu/wslc-ai-agent/blob/main/docs/plugins.md).

## Good to know

- The agent works with **WSL 3.0.0 or later**; the installer and
  `check-prereqs.ps1` say so of an older one. Volume events need
  **WSL 3.0.4**; capabilities, IPv6 networks and exec events **WSL 3.0.5**.

## Updating

```powershell
irm https://berpiztu.github.io/wslc-ai-agent/install.ps1 | iex
```

The agent's API goes from level 55 to 56, which only adds: clients of 1.9
keep working with this agent, and say a newer client is worth installing.
