## Security: ASP.NET Core's remote code execution is fixed

This version is built on **.NET 10.0.13**, the security release of
13 October 2026. The agent serves its web page with ASP.NET Core, and every
.NET 10 before it, up to 10.0.12, carries two vulnerabilities of **high**
severity that allow **remote code execution**:
[CVE-2026-102870](https://github.com/advisories/GHSA-g27p-qf6j-c96c) and
[CVE-2026-96230](https://github.com/advisories/GHSA-qjpx-jqm5-h2c4).
Both are fixed here, in the agent and in the clients, which carry the
runtime inside, with the other fixes .NET 10.0.13 brings.

## Every image the agent builds is checked for vulnerabilities

Every image this agent builds, from a Compose project (`wslc-compose up`,
`build`, or the Compose window) or from **Build image**, is checked before
any container is made from it. The agent reads the image's Python libraries
and its system packages (Alpine's apk, Debian's and Ubuntu's dpkg) from its
own files, so the versions are the ones it really carries, whatever its
requirements pin. It never runs the image: a scanner that runs what it
scans runs whatever the image hides. It asks the public vulnerability
database, [OSV.dev](https://osv.dev), about each one: GitHub's advisories
for Python, the distributions' own security trackers for the rest. A Python
library Debian or Ubuntu installed (`python3-flask`) is the distribution's,
which mends it without changing the version PyPI would read: it is checked
as its package, and no patch offers pip for it.

- **A library with a vulnerability moderate or worse stops the build.** No
  container is made from the image. The build's log names each
  vulnerability, with its advisory and the version that fixes it, and then
  says once per library the version that fixes all of its own, or that no
  version does yet and the library has to be replaced.
- **A lower one is written in the build's log**, and the build goes on.
- **The distribution rates its own packages.** A system package's severity
  is the one its distribution gives it, since the distribution decides
  whether and when a fix comes: Ubuntu's priority (`medium` is moderate),
  Debian's urgency on its release. A CVSS critical that Ubuntu rates medium
  is moderate. Only an advisory with no rating of its own (Alpine gives
  none, Debian's "not yet assigned" is none) takes the one of its GitHub
  twin, or else the one its CVSS score gives, version 3.x or 4.0 scored as
  NVD scores it, so a critical one never passes as unknown.
- **Zaindari**, Basque for safekeeper: *Zaindari: check vulnerabilities*, in
  a container's, a project's and an image's menu. It checks the image there
  and then, saying "Checking Zaindari - Vulnerabilities for …" beside a turning wheel, and
  shows only vulnerabilities: every known one, the low ones too, coloured by
  severity, with the version that fixes each, then a line per library, red
  when its worst is high or critical. What it finds marks the image again,
  worse, better or clean, and its containers read it. The image's libraries are read
  in the image itself once and kept by its id, and each advisory is kept a
  day, so it opens quickly, after a restart of the agent too. The menu
  offers it in red when the agent makes no container from the image or it
  has a high or critical vulnerability, in yellow when it has others.
  (`GET /api/v1/image-security/vulnerabilities`, and the
  `image_vulnerabilities` MCP tool; [how it works](https://github.com/Berpiztu/wslc-ai-agent/blob/main/docs/features/zaindari.md).)
- **And again before every new container**: Run, Create, View & edit's
  Save, an image update, a project's save. What was clean when the image
  was built may not be today. An image built on this machine with a
  vulnerability moderate or worse is refused, and nothing is touched: the
  container View & edit was to replace runs on as it was. An image from a
  registry is never refused, since it is not yours to mend; what it carries
  is said with the new container. A container that exists is started,
  stopped and restarted as always, whatever its image carries: what is
  guarded is what is made new.
- **What Zaindari finds belongs to the image**, kept on it by its id: two
  tags of two images are two marks, and an old tag can be red while a new
  one is clean. A container reads its image's mark, so the two never say
  different things.
- **Red and yellow where they are seen**: red for a high or a critical
  vulnerability, or for an image built here that the agent refuses, yellow
  for a moderate one. An alarm is raised only for what something can be
  done about: a fix the image can reach, or a Python library, which can be
  raised, replaced or taken out. A system package its distribution has not
  fixed for the image, which nobody downstream can mend, says `CVE` in grey
  on the state chip and is listed by Zaindari; the alarm comes back when the
  distribution publishes the fix. On the Images page a marked image is that colour from
  one side to the other, its whole row and its whole card. On Containers
  and on the dashboard, its containers' state chip says `running · CVE` in
  that colour, and so does their project's. Zaindari says what, and checks
  again: each library in the colour of its own severity, and the refusal in
  red on a line of its own. The container's logs and its project's are its
  own: what the check found is not written in them, since a log with no
  line about it would read as an image with nothing wrong.
- **Settings → Security → Image security check** sets what one moderate or
  worse does: stop the build (the default), only say it in the log, or no
  check at all.
- **A container's passwords are no longer written in the log.** Every
  `wslc` command the agent writes, in its log, in its activity and in an
  error shown to you, says each environment variable and build argument by
  its name with its value hidden (`API_KEY=***`), and so does what
  `container inspect` prints. A command that failed or ran too long was
  writing them whole.
- **View & edit's Save of an image not on the machine pulls it first**, as
  Update image does, shown on the Images page and on the container's row,
  then recreates the container with the settings saved. Left to the
  container's create, a large image failed at its minute.
- **Only running containers are checked on their own**: a container stopped
  for a month is checked when it is started again, not while it sits there.
- **The kernel is left out**: Debian's and Ubuntu's `linux`, whose headers an
  image carries, is not the container's, which runs on WSL's kernel; its
  hundreds of vulnerabilities no longer paint every Debian image red. Nor is
  what the distribution says is not a security problem for it, Debian's
  `unimportant` and Ubuntu's `negligible`, which it will not fix and nobody
  else can.
- An image with no package it can read, or of a distribution OSV.dev has no
  tracker for (Kali, `scratch`), is said to be unchecked, never clean. When
  OSV.dev cannot be reached, the log says so too and the build goes on.
- A system package is mended by building on a newer base image, or by an
  upgrade in the Dockerfile, and Zaindari says so beside the version that
  fixes it.
- **Ubuntu Pro**: a fix only Ubuntu Pro carries is said beside the
  vulnerability, "fixed only in Ubuntu Pro", and counted in what is left. In
  an image left attached to Pro (its ESM sources and their credentials in
  it), it is a fix like any other, which a patch's upgrade installs.

## Zaindari patches an image: a new image, made from the old one

When pulling an image again does not mend it, because its maker has not
rebuilt it yet or the fix is in a library it carries, the agent mends it
itself: **Patch** builds a new image from the old one, `…-patched`, with
what you change in it, and moves the containers to it.

- **Where**: *Patch* in Zaindari's window, opened for a container or an
  image; and *Patch…* beside the Version of a container's *Update image* and
  beside the Tag of its *View & edit*, the same window with that container
  alone ticked. It is in the warning colour when a fix is published that the
  image does not carry, and offered with none too, for a library to be taken
  out. The arrow beside it opens Zaindari's whole note: what a patch would
  mend, and what is left. While Zaindari is asked a wheel turns there, and
  Update, Save and Run wait for it.
- **The whole Dockerfile, read and changed before it is built**: `FROM` the
  image, its system packages upgraded when a fix is published that it does
  not carry (`apt-get upgrade`, `apk upgrade`), and its own user given back.
  Any line can be changed or added: what is built is what the window shows.
- **The image's Python libraries, a line each.** Beside the Dockerfile, the
  image's own `requirements*.txt` are listed line by line, with the
  vulnerable libraries they do not name, brought in by another. Each is
  kept, raised to the version that fixes it, taken to the latest or taken
  out (red and struck through); *All to latest* does it to every one. The
  file rewritten by the choices is shown whole, to copy back to the sources,
  and as each row is chosen the Dockerfile is given the lines that copy it
  into the image and install from it, with uv when the image has it, and
  loses them again when every row is kept: the Dockerfile shown is always
  what is built.
- **Checked like any build, and never refused**: what is left in a patch has
  no fix published and is its original's to mend. The window says what is
  left at its top.
- **The containers ticked move to it**, with their ports, mounts,
  environment and name; View & edit puts one back on its old image if the
  patch does not work. A project's containers are left as they are, since
  its compose file names the image. A container on a patch says *patched*
  beside its state, and a patch's *Pull* pulls the image it was made from.
- **A patch of a patch** builds on it, one step at a time.
- **Followed while it is built**: the image's and the containers' cards say
  *Patching: building …* beside a turning wheel, with a button that opens
  the build's log as it is written and one that cancels it, and the title
  bar's activity line follows it step by step. A build that fails, a
  patch's or any other, says the last line its failed step wrote
  (`No module named pip`), not its first step.
- **Build image takes a Dockerfile from your device**: pasted in its field,
  or loaded into it with the button beside it, and built by the agent with no
  folder on its machine. `FROM` an image and `RUN` what it needs: in an
  emergency, from a phone, an image is mended without its sources, a Python
  library raised (`RUN uv pip install --system -U "aiohttp>=3.13.6"`) or
  anything else, and Zaindari checks what comes out.

## Volumes say what happens to them

With **WSL 3.0.4**, `wslc` reports what happens to volumes, and the agent
listens:

- **Recent events**, on the dashboard, and the `recent_events` tool for AI
  agents list volumes created, mounted, unmounted, destroyed and pruned,
  each by its full name.
- **A screen that lists volumes reads them again the moment one changes**,
  as it already did for containers, images and networks.

With WSL 3.0.3 nothing changes: there are no volume events to hear, and
the volumes are read on the screens' own clock as before. The agent asks

running agent is picked up by itself.

## Build on another machine: your sources travel as a tar archive

Until now a Compose file with a `build:` could only be built on the machine
that had the folder. From this version you build **on a remote agent from
the sources on your own machine**: the build context is packed as a tar archive, sent
to the agent, and built there with `wslc build`, which reads a context from
its standard input since **WSL 3.0.3**. The images are made where the
containers will run.

It is how a deployment on a server is updated from the desk that has the
new code: the sources go, and the server's own data folders stay where they
are and are mounted as they were.

### From the command line

```powershell
wslc-compose --agent https://server.example.com --token … up -d --build
✔ Build context .: 2 of 2516 files, 51.9 MB sent (9.1 KB); the agent had the rest
```

- **Packed as `docker build` packs it**: without what the folder's
  `.dockerignore` leaves out, the Dockerfile always in.
- **Only what the agent lacks is sent.** Every file is hashed first and the
  agent says which it does not have. The first time that is the whole
  folder; after it, a Dockerfile changed in a folder of fifty megabytes
  travels as a Dockerfile.
- **It says how far it has got** as it reads, packs and sends.
- **Nothing is unpacked on the agent's disk**: it keeps each file once,
  under its hash, and makes the archive for the build itself.
- `up --no-start` builds and creates the containers and leaves them
  stopped; `build` makes the images alone.
- **A first project, step by step**: the counter
  (`docs/compose/examples/counter`), from the Compose file to another
  machine.

### From the Compose window

- The **Open Compose file** and **Context** buttons are a menu: **From this
  device** or **From the server**. A new picker shows the server's disk and
  its Compose files from any client.
- From this device, on another machine than the agent's, the window asks
  for the path of the folder the file is in, and then for the file. That
  folder is the context.
- **Save** and **Run** send what the images are built from, and do it
  **with the window closed**: the folder is read first, which takes
  seconds, the usual question is asked, and the sending goes on behind
  while the title bar's line and the transfers list say how far it has got.
- A project made this way is opened again (**View & edit**) as it was
  made: its file by the path it has on your machine, its context your
  folder. Saving it asks for the folder and sends what changed, or, in the
  same window, builds from **what the server has**: the folder as it was
  sent the last time, with nothing read from your device. That is how a
  variable is changed from a phone, or from any machine without the folder.
  The agent keeps those sources for as long as it keeps the project.

### One folder, the same on both machines

Only the sources travel. What the file mounts by a relative path, its
`.env` and its `env_file` are the server's, at the same path the project
has on your machine; a folder it mounts that is not there yet is made when
its containers start. A project that already lives somewhere on the server
stays there, and `--project-directory` names another place.

### The sending is one of the agent's transfers

It is in the transfers list of every client, with its progress and a cross
that stops it, and **the agent does not update itself while something is
travelling**.

- **Containers, Volumes and Networks** read their lists every five seconds,
  so the dials on their cards follow what is happening: a container's CPU
  and memory, a volume's bytes read and written, a network's traffic. An
  event says a container started; it says nothing of what it reads, writes
  or sends afterwards, and read on the events alone a dial stood still for

- **Warnings and errors are never lost.** Whatever a client shows as a
  warning or an error (a toast, the title bar's line, an error window, what
  `wslc-compose` prints) is written in the agent's log too. Warning toasts
  now stay until they are closed, as errors do.

  (`-y` answers yes; with no terminal to ask on, it stops there). The agent
  itself refuses such a save unless the client says it replaces the file,
  so a client of an earlier version stops with that error and changes
  nothing.
- **View & edit's Save closes at once**, as Run does. The agent checks the
  image, rehearses the new settings and replaces the container on its own,
  and finishes it even when the window or the browser goes; the title
  bar's line says how it ends, and a recreate that did not happen opens a
  window that says why.
- **What is done around the agent shows.** `wslc` run by hand or by a
  script goes straight to WSL, and nothing can stop it; the agent now sees
  the state it leaves. A container it did not make has its image checked
  as soon as it appears, when the image has no mark yet, and shows its
  image's mark. A project one of whose services no longer has a
  container is yellow too, and a container that took that container's
  name is yellow; what depends on the missing service cannot start, and is
  red, and so is its project. It is all written where it is read: in the
  agent's log, at the end of the project's logs, of its Save log and of

  container again, once the name is free.

  started again, and what depends on the missing service does not start,

- **A project's file is kept when its save begins**, not once it has gone

- **Warnings that read on the light theme**: a log's warning lines, a

  their yellow ground.
- **Log viewers**: an INFO line is in the theme's own text colour, black on
  the light theme and white on the dark; the light blue it had was barely
  read on either. Info, Warning and Error are three keys on the rail, each
  in the colour its lines wear, all held down at first: held down, sunk
  into the rail, their lines are shown; let up, they are hidden. A line
  with no level goes with the one above it. The level list hidden in the
  search is gone. Every button on a rail now stands a little prouder, so a

- **The README tells where the project comes from**: a Python dashboard in

## Good to know

- The agent works with **WSL 3.0.0 or later**; the installer and
  `check-prereqs.ps1` say so of an older one. Volume events need
  **WSL 3.0.4**, a preview of WSL today.
- Building from a folder of another machine needs **WSL 3.0.3 or later on
  the agent's machine** (`wsl --update`). An older one is said before the
  build begins. Everything else works as before.
- In the Compose window, picking a folder of your device needs a
  Chromium browser (Chrome, Edge) over https, or the agent's own machine.
  A browser never tells a page where a folder is, so its path is asked for,
  in so many words, every time. The Android app cannot pick folders.
- A browser cannot open a file whose full path is longer than 260
  characters: such files are left out of what is sent, and named in a
  warning. `wslc-compose` reads them.
- The agent and `wslc-compose` have to be of this version on both sides to
  send a build context.

## Updating

A preview is never in GitHub's latest release, so the README's line does not
install it. This one does, and updates an agent already installed:

```powershell
& ([scriptblock]::Create((irm https://raw.githubusercontent.com/Berpiztu/wslc-ai-agent/v1.6.4/install.ps1))) -Version 1.6.4
```
