## Security: .NET 10.0.14, the day it came out

This version is built on **.NET 10.0.14**, the security release Microsoft
published on 25 October 2026. Our security watch,
[security-watch](https://github.com/Berpiztu/security-watch), which every
build of the agent asks before it is made, found it the same day: it stopped
the builds still on the SDK before it, 10.0.402, until they were made with
10.0.14's, 10.0.403, now fixed in the repository's `global.json`. It fixes
four vulnerabilities:
[CVE-2026-111497](https://cve.mitre.org/cgi-bin/cvename.cgi?name=CVE-2026-111497),
[CVE-2026-70197](https://cve.mitre.org/cgi-bin/cvename.cgi?name=CVE-2026-70197),
[CVE-2026-102870](https://cve.mitre.org/cgi-bin/cvename.cgi?name=CVE-2026-102870)
and [CVE-2026-114148](https://cve.mitre.org/cgi-bin/cvename.cgi?name=CVE-2026-114148),
in the agent and in the clients, which carry the runtime inside.

**Update every agent**, above all one reachable from another machine or
from the internet.

## A project's own window: every container, one beside the other

A project's containers used to be reached one by one, each through its own
menu. A project now has windows of two panes: its containers at the left,
each in its image's colour, and at the right what the one chosen needs.
Nothing closes them but Close, so container after container is seen to in
one place.

- **Project**, the first button of the project's card (and *Project* in a
  table row's menu): MudBlazor's tabs for the container chosen.
  **Information** is its card as the Containers page shows it, its image and
  version, state, ports, networks, when it was made, its CPU and memory
  dials read every five seconds, and its start or stop, restart, menu and
  remove. **Logs** are its logs. **Update image** is its own Update image.
  **Zaindari** is its vulnerabilities, what to accept and its patch, in
  tabs of their own with Save and Patch at the right end of their bar.
- **All**, first in the list: every container's information, one under the
  other, and the project's logs as one, each line said by its container.
  Update image and Zaindari wait while it is chosen: they are a
  container's.
- **Logs, Update image and Zaindari** are buttons of the card too, beside
  the Compose file and the Save log, each opening that window with its one
  tab. They do exactly what the container's own does: the window only saves
  going container by container.
- **A container under way shows its work.** While its image is pulled, its
  pane shows the pull's console; while it is patched, the build's log;
  nothing in it can be pressed until the agent is done, and its wheel turns
  in the list. A verb's veil covers that container's pane alone, from the
  click until the list has the container under way: another is chosen
  meanwhile.
- **Fixed and quiet.** The window takes the screen's size when it opens and
  keeps it; the list is on the logs' ground, the container chosen in the
  primary's tint, so its own red or yellow still says its image's mark; *Up
  to date: nothing to accept or patch.* is said where neither has anything
  to do.

## Which version an image is

A tag such as `latest` does not say which version a container runs. The
agent now reads what the image says of itself, and says it.

- **On every card.** A container's card says, on a line of its own, its
  image's tag and the version, `latest (1.23)`; an image's card says the
  version after when it was made. When it was made reads short:
  `Created 1h 25m ago`.
- **Where the version comes from**: the image's
  `org.opencontainers.image.version` label, which its maker writes; or else
  the one `*_VERSION` variable it sets, as the official images do, named
  short, `7-alpine (7.4.11, RedisVer)`, `PyVer` for Python's. Either may be
  the image it was built on's: an application built on `python` says
  Python's version until its own build writes the label.
- **Before it is pulled**: *Update image* says, under the Version, which
  version the tag is as its registry has it now, what the update goes to,
  and this machine's when it has another: `7.4.12 (RedisVer) in the
  registry; this machine has 7.4.11 (RedisVer)`. The registry is asked as a
  pull asks it, without a login; a private image's registry asks for one,
  and its version is known once it is pulled.
- **An image is read once**, by its id, and a pull or a recreate shows the
  new version within seconds.

## Every image the agent builds is checked for vulnerabilities

Every image this agent builds, from a Compose project (`wslc-compose up`,
`build`, or the Compose window) or from **Build image**, is checked before
any container is made from it. The agent reads the image's Python libraries
and its system packages (Alpine's apk, Debian's and Ubuntu's dpkg) from its
own files, so the versions are the ones it really carries, whatever its
requirements pin. It never runs the image: a scanner that runs what it
scans runs whatever the image hides. It asks the public vulnerability
database, [OSV.dev](https://osv.dev), about each one: GitHub's advisories
for Python, the distributions' own security trackers for the rest. A Python
library Debian or Ubuntu installed (`python3-flask`) is the distribution's,
which mends it without changing the version PyPI would read: it is checked
as its package, and no patch offers pip for it.

- **A library with a vulnerability moderate or worse stops the build.** No
  container is made from the image. The build's log names each
  vulnerability, with its advisory and the version that fixes it, and then
  says once per library the version that fixes all of its own, or that no
  version does yet and the library has to be replaced.
- **A lower one is written in the build's log**, and the build goes on.
- **The distribution rates its own packages.** A system package's severity
  is the one its distribution gives it, since the distribution decides
  whether and when a fix comes: Ubuntu's priority (`medium` is moderate),
  Debian's urgency on its release. A CVSS critical that Ubuntu rates medium
  is moderate. Only an advisory with no rating of its own (Alpine gives
  none, Debian's "not yet assigned" is none) takes the one of its GitHub
  twin, or else the one its CVSS score gives, version 3.x or 4.0 scored as
  NVD scores it, so a critical one never passes as unknown.
- **Zaindari**, Basque for safekeeper: *Zaindari: check vulnerabilities*, in
  a container's, a project's and an image's menu. It checks the image there
  and then, saying "Checking Zaindari - Vulnerabilities for …" beside a turning wheel, and
  shows only vulnerabilities: every known one, the low ones too, coloured by
  severity, with the version that fixes each, then a line per library, red
  when its worst is high or critical. What it finds marks the image again,
  worse, better or clean, and its containers read it. The image's libraries are read
  in the image itself once and kept by its id, and each advisory is kept a
  day, so it opens quickly, after a restart of the agent too. The menu
  offers it in red when the agent makes no container from the image or it
  has a high or critical vulnerability, in yellow when it has others.
  (`GET /api/v1/image-security/vulnerabilities`, and the
  `image_vulnerabilities` MCP tool; [how it works](https://github.com/Berpiztu/wslc-ai-agent/blob/main/docs/features/zaindari.md).)
- **And again before every new container**: Run, Create, View & edit's
  Save, an image update, a project's save. What was clean when the image
  was built may not be today. An image built on this machine with a
  vulnerability moderate or worse is refused, and nothing is touched: the
  container View & edit was to replace runs on as it was. An image from a
  registry is never refused, since it is not yours to mend; what it carries
  is said with the new container. A container that exists is started,
  stopped and restarted as always, whatever its image carries: what is
  guarded is what is made new.
- **What Zaindari finds belongs to the image**, kept on it by its id: two
  tags of two images are two marks, and an old tag can be red while a new
  one is clean. A container reads its image's mark, so the two never say
  different things.
- **Red and yellow where they are seen**: red for a high or a critical
  vulnerability, or for an image built here that the agent refuses, yellow
  for a moderate one. An alarm is raised only for what something can be
  done about: a fix the image can reach, or a Python library, which can be
  raised, replaced or taken out. A system package its distribution has not
  fixed for the image, which nobody downstream can mend, says `CVE` in grey
  on the state chip and is listed by Zaindari; the alarm comes back when the
  distribution publishes the fix. On the Images page a marked image is that colour from
  one side to the other, its whole row and its whole card. On Containers
  and on the dashboard, its containers' state chip says `running · CVE` in
  that colour, and so does their project's. Zaindari says what, and checks
  again: each library in the colour of its own severity, and the refusal in
  red on a line of its own. The container's logs and its project's are its
  own: what the check found is not written in them, since a log with no
  line about it would read as an image with nothing wrong.
- **Settings → Security → Image security check** sets what one moderate or
  worse does: stop the build (the default), only say it in the log, or no
  check at all.
- **A container's passwords are no longer written in the log.** Every
  `wslc` command the agent writes, in its log, in its activity and in an
  error shown to you, says each environment variable and build argument by
  its name with its value hidden (`API_KEY=***`), and so does what
  `container inspect` prints. A command that failed or ran too long was
  writing them whole.
- **View & edit's Save of an image not on the machine pulls it first**, as
  Update image does, shown on the Images page and on the container's row,
  then recreates the container with the settings saved. Left to the
  container's create, a large image failed at its minute.
- **Only running containers are checked on their own**: a container stopped
  for a month is checked when it is started again, not while it sits there.
- **The kernel is left out**: Debian's and Ubuntu's `linux`, whose headers an
  image carries, is not the container's, which runs on WSL's kernel; its
  hundreds of vulnerabilities no longer paint every Debian image red. Nor is
  what the distribution says is not a security problem for it, Debian's
  `unimportant` and Ubuntu's `negligible`, which it will not fix and nobody
  else can.
- An image with no package it can read, or of a distribution OSV.dev has no
  tracker for (Kali, `scratch`), is said to be unchecked, never clean. When
  OSV.dev cannot be reached, the log says so too and the build goes on.
- A system package is mended by building on a newer base image, or by an
  upgrade in the Dockerfile, and Zaindari says so beside the version that
  fixes it.
- **Ubuntu Pro**: a fix only Ubuntu Pro carries is said beside the
  vulnerability, "fixed only in Ubuntu Pro", and counted in what is left. In
  an image left attached to Pro (its ESM sources and their credentials in
  it), it is a fix like any other, which a patch's upgrade installs.

## Zaindari patches an image: a new image, made from the old one

When pulling an image again does not mend it, because its maker has not
rebuilt it yet or the fix is in a library it carries, the agent mends it
itself: **Patch** builds a new image from the old one, `…-patched`, with
what you change in it, and moves the containers to it.

- **Where**: *Patch* in Zaindari's window, opened for a container or an
  image; and *Patch…* beside the Version of a container's *Update image* and
  beside the Tag of its *View & edit*, the same window with that container
  alone ticked. It is in the warning colour when a fix is published that the
  image does not carry, and offered with none too, for a library to be taken
  out. The arrow beside it opens Zaindari's whole note: what a patch would
  mend, and what is left. While Zaindari is asked a wheel turns there, and
  Update, Save and Run wait for it.
- **The whole Dockerfile, read and changed before it is built**: `FROM` the
  image, its system packages upgraded when a fix is published that it does
  not carry (`apt-get upgrade`, `apk upgrade`), and its own user given back.
  Any line can be changed or added: what is built is what the window shows.
- **The image's Python libraries, a line each.** Beside the Dockerfile, the
  image's own `requirements*.txt` are listed line by line, with the
  vulnerable libraries they do not name, brought in by another. Each is
  kept, raised to the version that fixes it, taken to the latest or taken
  out (red and struck through); *All to latest* does it to every one. The
  file rewritten by the choices is shown whole, to copy back to the sources,
  and as each row is chosen the Dockerfile is given the lines that copy it
  into the image and install from it, with uv when the image has it, and
  loses them again when every row is kept: the Dockerfile shown is always
  what is built.
- **Checked like any build, and never refused**: what is left in a patch has
  no fix published and is its original's to mend. The window says what is
  left at its top.
- **The containers ticked move to it**, with their ports, mounts,
  environment and name; View & edit puts one back on its old image if the
  patch does not work. A project's move too: its compose file still names
  the original, so the agent records the service on the patch, and every
  save of the project brings it up on the patch and says so, while the file
  names that image and the image is the one patched; a file that names
  another, the original pulled anew, or the patch gone, and the service runs
  what its file says again. A container on a patch says *patched* beside its
  state, and a patch's *Pull* pulls the image it was made from.
- **A patch of a patch** builds on it, one step at a time.
- **Followed while it is built**: the image's and the containers' cards say
  *Patching: building …* beside a turning wheel, with a button that opens
  the build's log as it is written and one that cancels it, and the title
  bar's activity line follows it step by step. Every container of the image
  says it, on the Containers page and on its header on the Home, one the
  patch does not move as *Patching its image*. A build that fails, a
  patch's or any other, says the last line its failed step wrote
  (`No module named pip`), not its first step.
- **Build image takes a Dockerfile from your device**: pasted in its field,
  or loaded into it with the button beside it, and built by the agent with no
  folder on its machine. `FROM` an image and `RUN` what it needs: in an
  emergency, from a phone, an image is mended without its sources, a Python
  library raised (`RUN uv pip install --system -U "aiohttp>=3.13.6"`) or
  anything else, and Zaindari checks what comes out.

## Zaindari: accept what nobody can mend, in a part you do not use

A Python library is always raised, fix or no fix, since it can be raised,
replaced or taken out. Sometimes none of the three makes sense: no version
fixes the flaw yet, and it is in a part of the library your image does not
use, a library's own server in an image that only uses its client. Until
now the image and its containers stayed coloured until somebody upstream
published a fix.

- **Where**: *Accept…* in Zaindari's window, beside Patch, opened for a
  container or an image, and Zaindari's *Accept* tab in a project's window. It lists the image's Python libraries with a
  vulnerability moderate or worse that no version fixes, a row each, and the
  ones accepted already.
- **Ticked, with a reason**: say why once, for the rows ticked, and save. An
  accepted vulnerability is shown in grey in Zaindari's window with who
  accepted it, when and why, gives the image and its containers no colour,
  and refuses nothing.
- **For every version of the image**: an acceptance belongs to the image's
  repository, not its tag, so the next version you build keeps it.
- **Until a version fixes it**: that day the acceptance stops counting and
  the vulnerability alarms again, for a patch to take it. A vulnerability
  with a fix is never offered: it is mended, not accepted. Any other
  vulnerability alarms as ever.
- **Untick a row to withdraw it.** Acceptances are kept in
  `image-acceptances.json` and in the API
  (`/api/v1/image-security/acceptances`); an AI agent over MCP sees them in
  `image_vulnerabilities`, and accepting stays a person's decision.
  ([how it works](https://github.com/Berpiztu/wslc-ai-agent/blob/main/docs/features/zaindari.md#accept-what-nobody-can-mend-in-a-part-you-do-not-use))

## Ready for WSL 3.0.4

This version works with **WSL 3.0.3**, the official WSL, and is ready for

## The dashboard: designed once, for every screen

- **Screens.** Each page says how desktop and mobile open it, set in design
  on its landscape view with nothing selected. **Desktop view on mobile**
  shows the landscape view on a phone too, so a page needs no mobile view of
  its own; **Desktop zoom** and **Mobile zoom** are the fit each screen
  starts on (Fill and Fluid until set). A device that chooses another fit
  in its zoom window keeps its own, for each page and screen.
- **Fluid lays a page out in reading order.** What does not fit beside what
  stands before it in its row goes down to a line of its own, each line's
  pieces side by side from its top, nothing kept together but what you
  grouped. A piece or a card set to **New line in Fluid** always begins a
  line: two cards side by side in a project's card, one under the other on
  a phone where one fits, the card growing down and what is under it coming
  down too.
- **Preview** shows the view being designed, saved or not, in the screen it
  is meant for: the canvas size's width and height, a phone's for the
  mobile view, fitted as its zoom says. A tap selects a card, then a piece
  of it, and its properties change it there; **Edit** goes back to the
  cells. The title says the view, and whether it is Design or Preview.
- **Cards in cards, as deep as they are put.** An object let go in a card's
  free room joins it, and a whole card let go wholly inside another stands
  in it as a card of its own (a project's charts, its recent events), moved
  with it, and taken out again by carrying it out. A card can be made
  smaller than what stands in it.
- **Groups.** Pieces chosen together (Ctrl and a press on each) become a
  group with **Group** (Ctrl+G), moved, anchored and wrapped as one, on the
  level they were chosen on; **Ungroup** takes off that one level. The
  charts card is born with each of its four charts a group, so on a narrow
  screen a chart goes down whole, its figures with it.
- **Undo** (Ctrl+Z) goes back change after change, the last hundred.
- **A project's card is born with a place for its containers**, filled when
  its project is chosen, and again each time another one is, all at once or
  not at all. A group you make of containers' cards becomes that place.
  **Auto-expand** grows it down to hold more cards and **Auto-shrink**
  shrinks it to fewer, what is under it moving as much; each view keeps its
  own, so a phone's can grow while a desktop's stays as designed.
- **A project's containers as a table**: service, container, status, ports,
  CPU and memory, in the shape of Recent events. The dashboard's tables take
  the object's text and ground, keep each cell on one line, and a project's
  stopped containers keep a text colour chosen for them.
- **A chart can follow a Compose project**: its containers' CPU, memory,
  disk and network added up, read from the list the dashboard already has.
- **A project's ring is drawn on the dashboard too**, three times as thick
  as in the list, so its colour changing is seen from afar.
- **A new default dashboard** travels beside the installers: the
  dashboard's Tools offers to load it.

## Volumes say what happens to them

With **WSL 3.0.4**, `wslc` reports what happens to volumes, and the agent
listens:

- **Recent events**, on the dashboard, and the `recent_events` tool for AI
  agents list volumes created, mounted, unmounted, destroyed and pruned,
  each by its full name.
- **A screen that lists volumes reads them again the moment one changes**,
  as it already did for containers, images and networks.

With WSL 3.0.3 nothing changes: there are no volume events to hear, and
the volumes are read on the screens' own clock as before. The agent asks
`wslc` its version each time it begins listening, so updating WSL under a
running agent is picked up by itself.

## Also in this version

- **A red row's buttons are seen.** In a table, a row in the alarm's red
  (an image Zaindari refuses) or a project's tinted row keeps its actions
  cell in its own ground, so Delete's red is read on it.
- **A card's last line stays in the card**: a long one is cut where the card
  ends, and whole when the pointer rests on it, as every other line is.

- **Containers, Volumes and Networks** read their lists every five seconds,
  so the dials on their cards follow what is happening: a container's CPU
  and memory, a volume's bytes read and written, a network's traffic. An
  event says a container started; it says nothing of what it reads, writes
  or sends afterwards, and read on the events alone a dial stood still for
  a minute.
- **A project saved from another Compose file is asked first.** Two files
  that give themselves the same `name:` are one project, and saving the
  second took the first one's place without a word, its other services'
  containers left over for the next save to remove. The Compose window now
  stops in a red window of its own, naming the file the project was last
  saved from and those containers, and Replace waits until the project's
  name is typed; and `wslc-compose up` asks `Replace it? [y/N]`
  (`-y` answers yes; with no terminal to ask on, it stops there). The agent
  itself refuses such a save unless the client says it replaces the file,
  so a client of an earlier version stops with that error and changes
  nothing.
- **View & edit's Save closes at once**, as Run does. The agent checks the
  image, rehearses the new settings and replaces the container on its own,
  and finishes it even when the window or the browser goes; the title
  bar's line says how it ends, and a recreate that did not happen opens a
  window that says why.
- **What is done around the agent shows.** `wslc` run by hand or by a
  script goes straight to WSL, and nothing can stop it; the agent now sees
  the state it leaves. A container it did not make has its image checked
  as soon as it appears, when the image has no mark yet, and shows its
  image's mark. A project one of whose services no longer has a
  container is yellow too, and a container that took that container's
  name is yellow; what depends on the missing service cannot start, and is
  red, and so is its project. It is all written where it is read: in the
  agent's log, at the end of the project's logs, of its Save log and of
  each container's logs, where they open. Saving the project makes the
  container again, once the name is free.
  The project is answered as an update of it would be: what ran of it is
  started again, and what depends on the missing service does not start,
  so it sends nothing to a container that took the name. A restart policy
  keeps the same rule: a container starts only once what it depends on in
  its own project runs.
- **A project's file is kept when its save begins**, not once it has gone
  well: a save that fails leaves the project with the very file it tried,
  for View & edit to open and mend. Before, it left a project with no file.
- **A project's Save log**: a button beside its logs, in its row, its card
  and the dashboard's project shortcuts, opens the log of its last save or
  build however it ended. A save that went well left nothing to read once
  its row was gone.
- **Alarms in their own colours**: a container that failed, and its
  project, have their card in MudBlazor's red, and one whose image has
  known vulnerabilities in its yellow, with black text, in the Containers
  list and on the dashboard alike. The soft red they had was barely seen on
  the dark theme.
- **A project's card is its bracket's colour**, indigo while it is stopped
  and green while it runs, with white text and dials, in both themes: the
  faded pink it had read as a red on the dark theme. On every coloured card
  a dial is drawn in the card's text colour, its reading included.
- **Warnings that read on the light theme**: a log's warning lines, a
  patch's vulnerable rows and Zaindari's menu item are in a dark orange
  there; the yellow was barely read on the white. Cards, rows and chips keep
  their yellow ground.
- **Log viewers**: an INFO line is in the theme's own text colour, black on
  the light theme and white on the dark; the light blue it had was barely
  read on either. Info, Warning and Error are three keys on the rail, each
  in the colour its lines wear, all held down at first: held down, sunk
  into the rail, their lines are shown; let up, they are hidden. A line
  with no level goes with the one above it. The level list hidden in the
  search is gone. Every button on a rail now stands a little prouder, so a
  key held down reads at a glance. Until the first reading is in, a bar
  moves and the window says "Reading…": an image's libraries or a long
  history can take a while, and "No logs." read as nothing there.
- **The README tells where the project comes from**: a Python dashboard in
  June 2026, SSH and Entra ID, an agent in the user's session, the rebuild
